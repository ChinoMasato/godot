# BACKLOG — 検証ループの課題台帳

形式: 1件 = 判定方法（どのテスト／ベンチマークで良し悪しを決めるか）を必ず書く。
判定できない課題はここに入れない。

## Phase 0（基盤）

- [ ] B-001 ベースライン確立: フルビルド（tests=yes）を通し、単体テスト全件を実行して結果を記録する。判定: テスト総数と pass/fail の内訳が LEDGER に残ること。失敗があれば、それ自体が最初の修正課題になる。
- [ ] B-002 ビルド／テスト所要時間の計測をスクリプト化する（ai_loop/measure.sh）。判定: 実行すると所要時間が LEDGER 形式で1行追記されること。
- [ ] B-003 エンジン名を U.ZU Engine に変更する（version.py の name / short_name、関連する表示箇所）。ベースライン完了後に実施。判定: 変更後のバイナリが起動し、全テスト pass、--version の表示が U.ZU Engine になること。プロジェクト形式の互換に影響する変更（設定パスの扱い等）があれば先に千野へ確認する。

## Phase 1（観測可能性と実証）

- [ ] B-101 テスト結果を機械可読形式（JSON）で得る方法を確立する。まず doctest のレポータ出力で足りるか検証し、足りなければエンジン側の改修として切り出す。判定: 1コマンドで pass/fail 一覧の JSON が得られること。
- [ ] B-102 既存の小さいバグ修正をループで完走させる（対象は B-001 の結果と上流 Issue から選ぶ）。判定: 修正＋テスト追加で全テスト pass、LEDGER に完走記録。
- [ ] B-103 GDScript のエラー／警告のうち「発生箇所と直し方が読み取れない」ものを洗い出す。判定: 具体例つきの一覧ができ、最初の1件を構造化エラーの試験実装として切り出せること。

## Phase 3（自己検証プレイ／面白さの代理指標）

- [ ] B-301 プレイテレメトリの形式定義: 詰まり（同一箇所での死亡・停滞の集中）、離脱点、クリア到達を、作者と AI が読める JSON 形式で定義する。個人を追跡しない設計（コミュニティ単位の集計が既定）。判定: サンプルゲームのプレイログから形式通りのレポートが生成されること。
- [ ] B-302 AI ゲームプレイヤー連携の要件整理: ユーズ社の研究開発「AIゲームプレイヤー」がエンジン側に要求するインターフェース（入力注入、状態ダンプ、スクリーンショット）を洗い出す。判定: 要求一覧が設計書 Phase 3 の注記として残ること。

## Phase 5（パブリッシング）／Phase 6（コミュニティ、Gogashare 型）

- [ ] B-503 橋 API の契約定義: エンジン（制作側）とプレイ側プロダクトの境界を API として固定する — 公開（ビルドのアップロードとメタ情報）、感想・テレメトリの取得、試遊会のセッション情報。判定: 契約（エンドポイントと JSON 形式）の一覧が設計書の分離セクションに紐づく形で ai_loop/ に残ること。コミュニティ機能本体はエンジンに入れない（分離原則）。

- [ ] B-501 itch.io 公開の実証: butler CLI で既存の自作ゲーム（例: SIDE NOVA の Web 版）をテストページへ push し、差分アップロードまで確認する。エンジン改修の前に「公開パイプラインの形」を先に固める。判定: 1コマンドで公開ページのビルドが差し替わること。
- [ ] B-502 公開前チェックの最小版: ビルドサイズとライセンス表記（LICENSE／COPYRIGHT の同梱漏れ）を機械チェックするスクリプト。判定: 漏れのあるテスト用ビルドを検出して fail すること。
- [ ] B-601 構造化フィードバックの形式定義: 「詰まった場所／バグ／アイデア」を JSON スキーマとして定義し、AI バックログへ変換できることを小さなサンプルで示す。判定: サンプルの感想データが BACKLOG 形式の課題に変換されること。設計上の制約: 感想は点数化しない（星評価を持たない）。構造化するのは作者と AI が直すための情報だけで、感想の本文は「贈り物」としてそのまま作者に届く形にする。

## 保留（判定方法が決まったら昇格）

- ヘッドレス自動プレイテスト基盤（Phase 3）— 判定用のサンプルゲームと期待状態の定義が先。
- MCP 公式実装（Phase 4）— Phase 1 の観測可能性が前提。
- 独自ギャラリー／コミュニティ空間のバックエンド（Phase 5〜6）— U.ZU クラウド側の設計が先。エンジン側は API クライアントに徹する。
