## 1. スタイル定義のデータ化（最優先）

- 新規 `ai_loop/building_styles.json`: 様式 = `geometry`（階高・基礎高・壁厚・窓 {w,h,sill_offset,slot_margin,slot_spacing,skip_distance}・ドア・店舗ガラス・屋根 {rise_ratio_min/max, eaves}・煙突確率・tints・roof_tiles）と `materials`（plaster／brick／wood／roof_tile／flat_roof／trim／door／glass／stone／chimney_brick の手続きパラメータ）の2節。
- `building_recipe.py`: `resolve_style()` が `default` への deep-merge で解決。未知の様式名・未知キーは ValueError で拒否（黙って既定に落ちない）。派生 spec に `style_name` と解決済み `style` 全体が入り、Blender 側（`building_lib.make_materials`）も幾何定数と同じ style から素材パラメータを読む。**RNG の呼び出し順序は第1段と完全同一に維持**。
- 既定様式の再現検証: street_spec.json の5棟すべてで、新コードの派生結果が第1段コード（ai-native の building_recipe.py）と `style`／`style_name` キーを除き完全一致（IDENTICAL）。さらに house_plaster の GLB は同日のスモークランとバイト数一致（2,656,596 B）。
- 様式追加の実証（`alpine`、データのみ・コード変更なし）: 同一の家・同一シードで `style` 指定だけが違う2棟を生成（`ai_loop/look_samples/b1219_alpine/`、spec は同フォルダの alpine_spec.json）。派生値の差: roof_rise 2.224→3.467、eaves 0.45→0.7、floor_height 2.8→3.0、窓 0.9×1.3→0.8×1.1（間隔 2.2→1.6 で密に）、煙突確率 0.35→0.9、木目 board_scale 4.4→3.4。実用三角形 6,552（default）vs 8,018（alpine）、瓦 594 vs 756。render_c で屋根勾配・軒の深さ・窓密度の差が目視できる。
- 地形側の確認: UZUWorldGen の nature／city オプションは既に完全な Dictionary（JSON）駆動で、プリセット＋個別キー上書きで解決される（`resolve()`）。バイオームは既に JSON 1枚で定義・差し替え可能だった。実演（このブランチでビルドしたバイナリ）: `ai_loop/presets/map/biome_desert.json`（砂漠: plains ベース、水なし・木0・草0・雪なし・岩多め・砂色）を `--spec` でそのまま投入 → trees 0 / rocks 294 / data_files 4。同じシードの hills プリセット → trees 743 / rocks 144 / data_files 8。
  - ついでに `map_tool.gd` が `_` 始まりのキー（プリセットの `_about` 等のメタデータ）を resolve 前に落とすようにした。これでカタログ用に `_about` を持つプリセットファイルがそのまま spec として使える。`UZUWorldGen.resolve` 自体の厳密さ（未知キーはエラー）は変えていない。
  - **残り（非データ部分）**: city の `palette` は enum（warm／stone／modern／pastel）のままで、任意パレットのデータ差し替えは未対応。建物側の様式に相当する「色のデータ化」はここだけ残っている。

## 2. ORM/AO ベイク

- `building_lib.bake_building`（と岩の bake）に AO パスを追加し、`pack_orm()` で ORM（R=AO、G=roughness、B=metallic 0＝全素材が誘電体、A=1、Non-Color）をパック。書き出し素材は ORM → SeparateColor で G→Roughness、B→Metallic、R→「glTF Settings」グループの Occlusion に接続。
- GLB の実証（house_plaster.glb の JSON を解析）: images に `house_plaster_orm` が含まれ、baked マテリアルの `occlusionTexture` と `pbrMetallicRoughness.metallicRoughnessTexture` が両方とも ORM テクスチャ（index 1）を指す。全棟・全岩の stats に `orm_texture`、出力に `*_orm.png` と `*_ao.png`。

## 3. 品質指標の組み込み

- `building_lib.model_quality_metrics()`: エンジン側 `look rich` の model_quality と**同一の定義**（二面角 30〜60°=chamfer、75°超=sharp、bevel_share = chamfer/(chamfer+sharp)、triangles_per_m2 は表面積あたり、pbr_coverage は Base Color＋Normal に画像テクスチャが繋がった素材の三角形割合）で Blender ルートの実用メッシュを測り、stats.json の各棟・各岩に `model_quality` として記録。
- 街の値: bevel_share 0.91〜0.93、pbr_coverage 1.0（全棟）、triangles_per_m2 7.35〜14.38。
- `uzu.py look rich --blender-stats <stats.json>` でレポートに `blender_model_quality` としてマージ（bevel_share 極小と欠落率 >1% には hints）。実機検証: 見本 stats で5棟分がマージされ ok=true、不要な hint は出ない。

## 4. 内部フェースカリング＋瓦ジオメトリのインスタンシング

- カリング `cull_buried_faces()`: BVHTree のレイ偶奇判定（面の中心＋全頂点を法線方向へ 0.01 押し出した点が固体内部か、3方向多数決）。**全サンプルが埋まっている面だけ**を消すので、部分的に覆われた面・室内や開口に面した面は残る。join 直後・reduce 前に実行し stats の `interior_culling` に記録。
  - 削減（三角形数、カリング前→後）: house_plaster 7,432→6,743（453面）、house_brick 8,800→8,180（421面）、shop_wood 8,668→7,697（613面）、house_tall 12,076→11,256（538面）、house_small 3,492→3,101（252面）。全棟でカリング前後の鋭角エッジ数は不変（例 plaster 8,058→8,058）、後段 reducer の稜線保存率も 1.0 のまま。
  - 第1段→第2段の実用三角形（最終）: plaster 7,414→6,727、brick 8,766→8,150、shop 8,628→7,659、tall 12,046→11,230、small 3,492→3,101。
  - 正直な悪化点: ベイク欠落率は plaster 0.009%→0.023%、brick 0.146%→0.400%、shop 0.015%→0.173% とやや上がった（ケージ形状が変わるため）。全棟 ≤0.4% で実用上の問題はないが、改善ではなくトレードオフとして記録する。
- 瓦 `add_roof_tiles()`: 円弧プロファイル（4分割・8三角形）のシェルを1つの共有メッシュにし、切妻の両斜面に格子配置（行ごとに 4mm 持ち上げて重なり表現、slab との一致面回避）。**切妻のみ**——寄棟は斜めクリッピングが要るため対象外、陸屋根は瓦なし（どちらもベイク済みテクスチャの瓦目地が残る）。
  - 個数と追加三角形: plaster 594個（+4,752）、tall 500個（+4,000）、small 594個（+4,752）、alpine 対照 594／756個。GLB 解析で「メッシュ2つ（建物＋瓦）、瓦メッシュを共有するノード 594個」を確認。瓦パラメータ（半径・弧・長さ・間隔）も style の `geometry.roof_tiles` にデータ化済み。

## 5. 岩・自然物レシピ

- 新規: `ai_loop/rock_recipe.py`（`uzu.py rock`、CAPABILITIES 宣言つき）、`ai_loop/blender/rock_lib.py`、`ai_loop/blender/rock_main.py`。見本は `ai_loop/look_samples/b1219_rock/`（spec は同フォルダの rocks_spec.json）。
- 作り方: icosphere（細分化3）を種から派生した半空間でブーリアン切断（最初の1枚は必ず接地面）→ 小ベベルで稜線を整える → ハイ側は SIMPLE 細分化＋微変位＋手続き石素材 → 建物と同じベイク（ORM 込み）。比較レンダーは (a) ノイズ変位のみ（第1段 PoC の方式）(b) 面作りハイモデルのグレー (c) ベイク済み GLB。(a) は丸い塊、(c) は平面と稜線のある岩として読める。
- 数値: boulder_big ハイ 9,600 → 実用 608、欠落率 0.393%。boulder_wide 7,968 → 484、0.104%。shard_rock 6,464 → 408、0.036%。bevel_share 0.868〜1.0、pbr_coverage 1.0。
- **実測で踏んだ落とし穴2件**（コード内コメントにも記録）:
  1. 建物の reducer（12°未満の平坦エッジ dissolve）を岩に使うと形が崩壊する（約600→約75三角形、欠落率 24〜44%）。岩の浅い面間角度は形そのものなので、岩は weld のみ（remove doubles）にした。稜線保存率 1.0。
  2. 建物のケージ／レイ定数（押し出し 0.05、レイ距離 0.35）では岩の最大フェース2枚が丸ごと欠落した（boulder_big で 13.5%）。切り分け実測: 押し出し 0.15→48%、0.001→0%、レイ距離無制限→0%。大きな平面ではケージ面がレイ方向に遠く、距離上限で切れる。岩は凸形状で最初のヒットが手前表面になるため、ケージは建物定数のままレイ距離だけ無制限にした。
