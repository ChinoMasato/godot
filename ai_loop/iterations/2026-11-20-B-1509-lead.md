# B-1509 生成仕様の4点セット（2026-11-20、Muse lead branch）

マップ生成（B-1501〜1507）と宣言的シーン構築（B-1207）の出力に、生成の
「意図・観測・推論・検証」を分けた4ファイル（JSON）を揃えた。実装は
Python のみ（`ai_loop/spec_set.py` 新規）で、C++／生成器本体の変更なし。

## 使い方

- `uzu.py map <project> nature|city ... --spec-set [dir]`
- `uzu.py build <project> --spec spec.json --spec-set [dir]`
- MCP: `map_nature`／`map_city`／`scene_build` の `spec-set` 引数
  （`true` で既定位置、文字列でフォルダ指定）
- 出力先: 指定フォルダ（パスまたは res://）、省略時は生成シーンの隣の
  `<scene名>_spec_set/`。生成結果の戻り値 JSON に `spec_set`（ok・dir・
  files のパス）が入る。書き込み失敗は結果に明示され、生成自体は戻さない。

## 4ファイルのスキーマ

いずれも先頭に `format`（版）を持ち、時刻は入れない（同じ記録からは
同じセットが決定的に出る）。

### scene_spec.json（format: uzu-scene-spec/1）
- `intent`: 入力仕様そのもの（map は --spec＋--set を uzu.py 側で
  map_tool.gd と同じ読み方で再構成、build は仕様ファイルの中身）
- `parameters`: 解決済みパラメータ全件に `origin`（given＝入力にあった／
  defaulted＝生成器がプリセット・既定値で補った）。map は生成結果の
  `options` エコーが材料
- `observed`: 生成器が実測して返した事実（counts.*、places.*.position、
  navigation.*、三角形数、生成時間など）。各項目に `evidence`（由来の
  結果フィールド名）
- `inferred`: 補完した推論。各項目に `reason`。defaulted パラメータ
  （parameters.<key> として列挙）と、region_graph の辺の根拠
- `basis`: observed／inferred の区別基準そのものの文（下記）
- composite（合成）では部品ごとに `parts[]` へ同じ構造を入れ、合成全体の
  inferred（部品間の辺を主張しない理由）をトップに置く

### region_graph.json（format: uzu-region-graph/1）
- `nodes`: `{id, center:[x,y,z], about}`。map は生成器の places（単体は
  その名前、clearings／villages の配列は `clearings_0` 形式の連番 id）。
  build は仕様の models（名前と position）と Ground で、`basis: "given"`
  を付ける
- `edges`: `{a, b, length, bidirectional: true, basis: "inferred",
  length_basis}`。辺は観測された中心同士の最小全域木（MST、Prim 法、
  同点は (長さ, a, b) で決定的に選択）。長さは中心間のユークリッド距離
- composite は部品内にだけ辺を引き、id は `<マップ名>__<place>` で前置

### asset_registry.json（format: uzu-asset-registry/1）
- `families`: `{family, count, count_basis: observed|given, origin, note?}`
  - map: counts のキーごとに1ファミリー＋地形／全体の三角形数。
    origin は {generator, preset, seed}。建物など既知のキーには来歴の
    note（B-1219 の部品レシピ等）
  - build: ground／models（合計は observed、メッシュ別内訳は given）／
    scatter エントリごと（実数と target、seed）／lamps／particles／
    water／godrays。origin は {generator, spec}

### validation_report.json（format: uzu-validation-report/1）
- `checks`: `{id, claim, status, holds, evidence[]}`
  - status は証拠の強さ: Verified（実測の証拠がある）／Partial（証拠が
    部分的・混在）／Unverified（証拠が取れない）
  - holds は主張への支持: true（支持）／false（実測が否定。例:
    roads_connected=false は Verified＋holds=false と正直に残す）／
    null（判定材料なし）
  - evidence は `{type: "value", ref, value}` または
    `{type: "file", ref}` の列で、空の check は作らない（コード側で
    強制し、テストでも全件確認）
- map の check: generation_succeeded／counts_reported／places_reported／
  navigation_baked（city）／places_connected（city）／roads_connected
  （nature で村があるとき）／collision_coverage（現状 Unverified:
  生成結果に当たり判定の集計が無いため。B-1511 が保存物から監査する
  領分）／walk_reachability（設計上 Unverified: 実歩行は B-1510）
- build の check: scene_saved／models_placed／scatter_placed_<i>
  （target 未達は Partial＋holds=false）／richness_report（uzu.py が
  付けた report を材料。--no-report 時は Unverified）／
  walk_reachability（Unverified）
- composite は部品ごとの check に `<部品名>__` を前置し、全体の
  generation_succeeded と cross_part_reachability（Unverified）を追加

## observed／inferred の区別基準

- **observed** = 生成器自身が生成の結果として実測し、戻り値に載せた
  事実。由来フィールドを evidence として必ず併記する
- **inferred** = 実測なしに補ったもの。入力仕様に無く解決時に補われた
  パラメータ（プリセット・既定値由来）と、観測された位置から導いた
  接続（region_graph の辺）。理由を reason として必ず併記する
- 判定に使った実測が主張を否定した場合も、証拠の強さ（status）と
  支持（holds）を分けて残し、格上げも隠蔽もしない

## B-1510 への引き継ぎ

- region_graph.json の nodes（id と center）と edges（a／b／length、
  双方向）がそのまま歩行対象になる。id は合成では `<マップ名>__<place>`
- 辺は MST なので本数は nodes−1。歩行の合否は辺単位で返し、
  validation_report の walk_reachability（Unverified）を実歩行の結果で
  置き換える想定
- 注意: 辺の長さは中心間の直線距離で、実際の歩行距離ではない。
  tallest_roof のような高所の place もノードに含む（生成器の places
  そのまま）。歩けない辺は fail として返るのが正しい設計

場合の生成器のフォールバック）。
