## 内容

- **エンジン**（`scene/resources/uzu_pbr_from_image.{h,cpp}`、新規）: `UZUPBRFromImage`（静的メソッドだけのクラス）。試作 `ai_loop/prototypes/picture/pbr_tool.gd` を、同じ手順・同じ値で C++ に移した。
  - `get_kinds()`: 10種（stone、brick、cobble、ground、wood、plaster、fabric、leather、metal、painted_metal）の値。
  - `make(image, kind = "stone", options = {})`: 画像と ORMMaterial3D を返す。
    - options: strength、delight、tile、invert、size、normal（外部の法線マップの Image）。
  - `make_file(in_path, out_dir, kind, options)`: albedo.png、normal.png、orm.png、height.png、material.tres を書く。options に `normal_from`（パス）が使える。
  - `compare(normal, reference, orm, reference_orm)`: 平均の角度誤差、平らな法線の場合の誤差、roughness の相関。
  - 登録した。ドキュメント `doc/classes/UZUPBRFromImage.xml`（新規）も追加した。
- **試作からの意図的な変更は1点**: ぼかしの縮小を、bilinear から「区画の平均」に変えた。
  - 試作のぼかしは、Image.resize（bilinear）で 1/64 などに縮めてから拡大していた。bilinear の縮小は、平均ではなく、ところどころの1画素を拾う。
  - そのため、規則的な模様では拾う画素がそろって目地に乗り、「焼き込まれた光」の推定が外れる。テストの合成の石畳では、delight がほとんど効かなかった（右端と左端の明るさの比 2.6 → 2.0）。
  - 区画の平均に直したあとは、テストの基準（差が元の6割未満）を満たす。拡大は、試作と同じ cubic のまま。
- **ツール**（`ai_loop/`）:
  - `engine pbr-make --in --out [--kind] [--strength] [--delight] [--tile] [--invert] [--size] [--normal-from]`
  - `engine pbr-compare --normal --ref [--orm --ref-orm]`
  - `engine pbr-kinds`
  - MCP: pbr_make、pbr_compare。
  - `uzu.py selftest engine` に3項目を足した（作る、自分自身と比べて誤差がほぼ0、知らない種類は誤り）。
- 試作の `pbr_tool.gd` と `pbr_preview.gd` は、試作として残した（preview は GPU での確認用で、B-904 とローカル担当が使う）。

## 確認

- 単体テスト: `tests/scene/test_uzu_pbr_from_image.cpp`（新規、5件）。合成の石畳（256x192、高さ＝明るさ、左から右へ 0.3〜1.0 の強い光）で確かめた。
  - **albedo**:
    - 左右の明るさの比は、元が 1.8 超。albedo では、元の差の6割未満に縮む。
    - 「uneven lighting」の警告が出る。
  - **height**: 本当の高さとの相関が 0.8 超。
  - **normal（OpenGL）**:
    - R は −dh/dx と、相関 0.6 超。
    - G は +dh/dy（行は下向き。G が上）と、相関 0.6 超。
  - **ORM**:
    - 目地は、石の中央より AO が暗く、roughness が高い。
    - metallic は 0。
    - roughness の平均は、stone の基準値（0.82）の近く。
  - **material**: 法線が有効で、3枚のテクスチャを持つ。
  - **options**:
    - metal は metallic が 1。
    - invert で高さの相関が −0.8 未満になる。
    - size で縮む。
    - tile で、左端の法線が右端を見る。
    - 外部の法線マップに置き換わる（大きさと形式もそろう）。
    - 誤り（知らない種類、空の画像）。
  - **compare**:
    - 自分自身との誤差は 0.5° 未満で、相関は 1。
    - 平らな法線マップでは「作った物」と「平ら」の誤差が一致する。
  - **files**:
    - 5つのファイルが書かれる。
    - material.tres を読み込める。
    - 読めない入力と読めない法線は誤りになる。
- 全テスト: **1510件中 1510 pass**（5件増えた）。ビルドの警告: なし。clang-format: pass。
- **試作との一致**（雑音のある合成の石畳 384x288、本当の法線を計算で作り、`pbr-compare` で測った）:

  | 比べたもの | 法線の角度の差 |
  |---|---|
  | 試作 対 本当の法線 | 10.00°（平らなら 10.75°） |
  | C++ 対 本当の法線 | 9.54°（平らなら 10.75°） |
  | C++ 対 試作 | 0.66°（roughness の相関 0.94） |

  - albedo の左右の明るさの比: 元 1.65 → 試作 1.16、C++ 1.18。
  - 雑音のある模様では、試作の縮小の問題はほとんど出ない。結果は試作とほぼ同じで、本当の法線には少し近い。
- **実スキャンとの角度誤差**: このクラウド環境からは Poly Haven に接続できない（プロキシが拒否）。
  - 試作での測定（cobble 14.2° 対 平ら 14.9°、brick 18.6° 対 18.1°、rock 9.1° 対 8.4°、Q13 と試作の README）が、ほぼ同じ手順の結果として当てはまる。上の表のとおり、C++ と試作の差は 0.66° 程度。
  - スキャンを持っているローカル担当が、`engine pbr-compare` で測り直す。正直な前提は変わらない: 1枚からの法線は「平ら」と同程度が限界で、画質の主役は外部モデルの取り込み（B-903）。
- `uzu.py selftest all`（engine／selfplay／tools）: ok。
- ドキュメント: UZUPBRFromImage.xml に誤りも警告もない。全体の13件の誤りは、今回より前からあるもの。
