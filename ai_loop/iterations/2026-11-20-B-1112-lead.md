# B-1112 手触りの代理指標（Muse / lead branch、2026-11-20）

juice の効きを「気持ちいいか」でなく測れる代理指標で返す道具一式。
判定はしない。比較（前回／プリセット違い／juice 無効時）の材料を出すまで。

## 作ったもの

- `ai_loop/selfplay/feel_probe.gd`（新規）: プローブ autoload。
  `--uzu-feel <path>` があるときだけ動き、プロセスフレームごとに
  UZUJuice の適用状態（Engine.time_scale、UZUJuice.applied_time_scale、
  trauma、kick）をサンプルする（変化があったフレームだけ記録＋600
  フレームごとのハートビート）。watch 指定（`NodePath:property`、
  または `find:<名前>:property` の名前検索）で任意ノード値も同時記録。
  UZUUIJuice のイベントログをフレーム付きで転記し、使われた
  イージングプリセットの曲線サンプル点（motion_value を t=0..1 で
  21 点）も残す。`--uzu-feel-selftest` ではプローブ自身が
  hitstop／shake／slowmo／kick をスケジュール発火する（どの
  プロジェクトでも全チャネルを通せる）。
- `ai_loop/feel_report.py`（新規）＋ `uzu.py feel-report`:
  解析（セグメント抽出・イベント帰属・2レポート比較）とドライバ。
  プレイモードは verify_playthrough.py の経路をそのまま使い、
  プローブ入りで完走を測る。
- `ai_loop/aiplayer.py`: Game に `extra_autoloads`／`extra_user_args`
  を追加（既定 None で従来どおり。後方互換）。
- `ai_loop/samples/hikari/main.gd`: 最小フック。ユーザー引数
  `--uzu-no-juice` で UZUJuice／UZUUIJuice の効果呼び出しを全て
  無効化する（パネルの可視は最終状態が同じになるよう揃えた。
  juice_events の記録自体は両モードで残る）。
- 見本レポート: `ai_loop/samples/hikari/feel_report.json`（juice
  有効＋無効版との比較入り）と `feel_report_no_juice.json`。

## 指標の定義

- セグメント = 値がベース（time_scale は初回サンプルの scale、
  trauma／kick はエンジン自身の収束閾値 1e-3 以下、watch は最初に
  見えた値）から離れている連続区間。長さはプロセスフレーム数と
  壁時計 msec の両方で出す。ラン終了時点で継続中のセグメントには
  `"open": true` を付ける（収束したと偽らない）。
- time_scale セグメントは kind（hitstop = 最小 scale 0、slowmo =
  ベース未満、speedup = ベース超）と最小／最大 scale を持つ。
- trauma／kick は peak、半減までのフレーム数、ゼロ交差回数、曲線
  サンプル列そのものを持つ。
- watch セグメントはベースからの最大偏差（色なら成分最大）を持つ。
- 入力→反応の遅延 = 帰属した最速セグメントの開始物理フレーム −
  ドライバが interact を押した物理フレーム。帰属は「押した後
  240 物理フレーム以内に始まったセグメントを、最も新しい押しに」
  という規則。
- UI はイベント（count_up 等の start／end、プリセット名つき）と
  曲線サンプル点で出す。

## 実測値

プローブ自己テスト（sample_game、実時間実行）:
- hitstop(0.06s 要求): 9 フレーム / 62 msec、min scale 0.0
- slowmo(0.3 で 0.3s 要求): 44 フレーム / 304 msec、min scale 0.3
- shake(0.6): peak 0.6、55 フレーム / 379 msec、半減 28 フレーム
- kick(0.8): peak 0.8、主セグメント 65 フレーム / 448 msec、
  以後 0.015 → −0.0021 とバネの ringing が減衰セグメント列として
  見える

『灯りの欠片』完走（種 7、juice 有効）:
- 収集 ×3: 遅延は全て 1 物理フレーム。flash（プレイヤー modulate）
  は各回 20 フレーム / 約 120 msec（要求 0.12s どおり）、最大偏差
  0.6883（金色への mix ほぼ最大）
- 点火: flash 20 フレーム / 120 msec（偏差 0.6358）＋ kick
  peak 0.68、主セグメント 64 フレーム / 685 msec、半減 17
  フレーム、ゼロ交差 2
- ゲージの count_up（ease_in）イベントと曲線がイベント単位で取れる

juice 無効（`--uzu-no-juice`、同じ経路・同じ種）:
- UZUJuice の全チャネルが 0（flash セグメント [有効 1 → 無効 0]、
  kick [3 → 0] が比較表に数値で出る）
- count_up イベントは 4 件 → 0 件。ゲージはイージングなしで即時に
  跳ぶ（watch サンプルで段差として見える）
- ゲーム自体は両モードともクリアし、チェックポイント順序と
  juice_events は同一（無効化は効果だけを消す）

## 正直な限界（測れないもの・歪むもの）

- UZUJuice の締切は壁時計だが、ロックステップ中はドライバの
  思考時間だけゲームが止まる。プロセスフレーム数は実行形態で
  伸縮する（無効でないヒットストップ等は特に）。**信用できる単位
  は msec の方**で、フレーム数は併記に留める。対策として対話後に
  実時間の settle（1 フレームずつ＋小さな sleep）を入れてあり、
  これがないと flash が次の収集と融合したり kick がラン終了で
  切れたりする（実測で確認した失敗）。
- `--fixed-fps` の無調整実行では壁時計がほぼ進まず、60ms の
  ヒットストップが 1500 フレームのラン全体より長生きする。
  自己テストはそのため実時間実行にしている（プローブの start
  記録と本記録に明記）。
- パーティクルバーストと SE は測っていない（ノード数や音の
  指標は別系統の話）。flash／squash は watch に指定したノード
  だけ。hikari では squash を使うイベントがないので未実測。
- ゲージのような「状態」型の watch はベースに戻らないため
  1 本の open セグメントになる。収集ごとの内訳は UI イベントと
  曲線で読む設計（セグメントの意味は「効果の区間」であって
  「状態の履歴」ではない）。
- 帰属の窓（240 物理フレーム）と press フレームの定義
  （コマンド送信直前の観測フレーム）には ±数フレームの曖昧さが
  ある。遅延 1 フレームは「次の物理フレームで反応」と読む。
