### 問題1 追補【事前計算】静的な世界は開発時に焼く（オーナー指摘 2026-11-21）
- 指摘: 「スタティックな情報ならゲーム開発時に計算しておけば？」。村は
  シード固定の決定的生成なので、そのとおり事前計算が可能だった。
- 方式の判断: ナビメッシュ単体の事前計算ではなく、生成世界まるごとの
  事前生成（シーン同梱）を採用。理由:
  - ベイクは generate_city の内側（エンジン側）で走っており、ナビだけを
    切り出すには生成 API に事前ベイク済みメッシュを渡す口の新設が要る。
    一方、世界まるごとは既存の compose_village.gd（PackedScene 化）の
    前例があり、エンジン変更なしで実現できる。
  - 実測ではナビベイクは村ステップ ~160ms のうち bake_ms=50.2ms に過ぎず、
    ナビ単体では地形 ~300ms・池 ~240ms が残る。まるごと焼けば生成の
    全 673ms（bake_world.gd 実測）が消える。
  - テキスト .tscn の読み込みは 1,279ms と生成より遅かったため、保存形式は
    バイナリ .scn（3.8MB、読み込み ~10ms＋インスタンス化 ~10ms）。
- 実装:
  - bake_world.gd（新規ツール）: build_generated_world で生成し、指紋を
    ルートの meta（uzu_baked_fingerprint）に刻んで res://baked_village.scn
    へ保存。生成 673ms / 保存 15ms、建物6・街路樹26・land_y -1.664・
    ナビ 603 頂点 / 652 ポリゴン・places_connected=true（生成同一性は従来値と一致）。
  - main.gd: world_fingerprint() = JSON 化した 3 スペック＋構築バージョン
    （WORLD_BUILD_VERSION）の md5。_build_world_phased は最初に
    _try_adopt_baked_world() を試し、ファイル無し／指紋不一致／破損の
    いずれでも従来のステップ生成にフォールバックする。ベイクはキャッシュで
    あり、正本は常にスペック＋生成コード。
  - 採用時の city_result は places のみに縮約（ゲームが rc から読むのは
    plaza 位置だけで、障害物導出の残りは市ノードのツリーから読むため）。
    height_at は解析式で、焼いたノードでも生成直後と同値（4 点で照合済み）。
- 検証（headless、同ハーネス・同バイナリの 3 方式比較）:
  - 押下→start: 同期 758ms / 段階生成 762ms / ベイク採用 191ms。
  - 押下後の最長フレーム: 704ms → 302ms → 98ms。50ms 超フレーム: 1 → 4 → 2。
  - つまり分散は「総時間据え置きで最長フレームを半減」、事前計算は
    「総時間そのものを 1/4 にし、最長フレームも最小」。併用（ベイク優先＋
    フォールバックは段階生成）が最終形。
  - verify_playthrough.py（新バイナリ）: ベイク採用時 pass ×2 回
    （開始ハッシュは段階生成時と完全一致 44136fa3…）。ベイクを外した
    フォールバックでも pass。なおベイク採用の初回実行で 1 ランだけ
    ランタン前で AI プレイヤーが止まり未クリアがあった（欠片3・開始
    ハッシュ正常、負荷の高い時間帯）。再実行 2 回は両ラン pass。
    ランタン台座は作中で最もきつい障害物で、接近の成否がフレーム
    タイミングに敏感な箇所。世界データの差異ではないと判断するが、
    生成方式側で 6/6・ベイク側で 5/6 の標本であり、断定はしない。
- 状態: 完了。Web 実機での読み込み時間は未計測（書き出し後に要確認）。

## 問題2【フォント欠け】UI の日本語に □ が出る
- 原因: art/game_font.ttf のサブセット（197 グリフ）がタッチ UI（B-1004）と
  読み込みラベル（前回修正）より前に作られており、それらが使う 13 文字が無い。
  欠け文字（実測）: … み ィ キ ッ テ ボ 中 定 左 決 読 込
  ＝「読み込み中…」「左スティック」「ボタン」「決定」が化ける。オーナーの
  スクショ（左下の操作説明・右下ボタン）とも一致。
- 修正:
  - make_game_font.py（新規）: フル Noto Sans CJK JP（TTC face 0）から再生成。
    保持 = ゲーム内文字列の全文字（check 側の収集と共通）＋ ひらがな・カタカナ
    全域 ＋ CJK 句読点・全角形・基本記号。最終結果 614 グリフ / 233.7 KB
    （旧 197 グリフ / 110 KB）。
  - check_font_coverage.py（新規）: 全 .gd の文字列リテラル＋ ui/*.json /
    ui/*.tscn を収集し、フォント cmap と突合。欠けがあれば一覧つきで fail。
- 検証: 再生成前 check = fail（欠け 13 文字を検出）→ 再生成後 check = pass
  （used 203 文字、missing 0）。
  - エンジン側でも照合: Font.has_char でラベル・ボタン・読み込み文言の
    全文字を確認 — 旧フォントは 18 文字分が欠け（ラベル内の 13 文字＋
    読み込み文言の 5 文字）、新フォントは欠け 0。なお has_char の確認には
    明示的な --import が必要だった（worktree の .godot/imported キャッシュが
    再生成前のフォントのままで、--script 実行は再インポートしない）。
    書き出し時はソースからインポートされるため実害はないが、計測系の
    落とし穴として記録する。
  - 撮影での目視確認について（正直な記録）: VM の editor 環境では欠け文字が
    システムフォントのフォールバックで埋められてしまい、旧フォントの
    before 撮影でもラベルが正しく描画された（before/after のラベル切り抜きが
    バイト単位で一致）。つまり VM 撮影では豆腐の再現・解消を確認できない。
    オーナーの iPhone Web 版にはシステムフォントのフォールバックが無いため
    豆腐が出たのであり、フォント自体に文字を持たせる今回の修正が正しい
    対処。検証の柱は cmap 突合（fontTools）＋ has_char（エンジン）＋
    check_font_coverage.py の機械チェック。
- 状態: 完了。

## 問題3【UI背景がチープ】羊皮紙の繰り返しパターン
- 原因の当たり: scene/gui/uzu_ui.cpp の draw_frame は 9 分割の中央タイル
  （FRAME_TILE=32px）を TILE_FIT で繰り返し、羊皮紙の material_color は
  周期 32px の tile_noise（セル 8px、暗転最大 ~0.17）で模様を作る。
  幅 ~1000px の会話窓では同じ 32px 模様が約 30 回繰り返され「印刷パターン」に見える。
- 方針: FRAME_TILE を大きくし（繰り返し周期を伸ばす）、羊皮紙は大きなスケールの
  ムラ＋微細ノイズの低コントラスト合成に変える。テストは性質ベースに更新する。
- 実施（scene/gui/uzu_ui.cpp）:
  - FRAME_TILE 32 → 128（繰り返し周期を 4 倍に）。
  - 羊皮紙レシピ: セル 64px の swell（0.05）＋ セル 32px の drift（0.035）＋
    微細グレイン（0.015）の低コントラスト合成に変更。旧は セル 8px で最大 ~0.17。
    全成分ともタイルで割り切れる周期なので継ぎ目のなさは維持。
  - 影響範囲: draw_frame を使う全世界観テーマ（枠・ボタン・会話窓・名前タグ等）。
    他マテリアルは周期が 128 になるだけで模様のスケールは不変。
- テスト（tests/scene/test_uzu_ui.cpp）:
  - 既存の「32px 前提」を stylebox のマージンからタイル幅を導く形に変更。
  - 羊皮紙の新規ケース: タイル幅 ≥ 96、輝度の振れ幅が 0.015 超
    （真っ平らでない）かつ 0.12 未満（低コントラスト）、隣接ピクセル差の
    平均 < 0.01（細かい模様がない）。
  - 継ぎ目の検証は当初 pixel(x) と pixel(x+tile) の一致で書いたが、これは
    フレーム縁の「焼き縁」暗転（マージン側にだけ効く、タイル対象外の効果）を
    巻き込んで fail した（実測で切り分け: x=20,21 のみ不一致、差は縁からの
    距離で単調）。実際の継ぎ目は「タイル最終列と先頭列の隣接」なので、
    その輝度差 < 0.03 の確認に置き換えた。
- 検証: エンジン全テスト 1578 件中 1576 pass。fail は既知の環境起因
  [UDPServer] 2 件のみ（自分の変更分は全 pass）。
  - 撮影比較（capture_ui.py、タッチ UI 有効、~/workspace/hikari-fix2-captures/）:
    会話窓 before は全面に規則的な織り目状の繰り返し模様が見える（まさに
    「印刷パターン」）。after は同じ窓が滑らかな羊皮紙になり、緩やかな
    濃淡の流れだけが残った。HUD の小パネルでも斑点模様が消えたことを確認。
- 状態: 完了。
- 備考（問題1の進捗ラベル撮影）: ベイク採用で開始全体が ~190ms になったため、
  VM では読み込みラベルの撮影はできなかった（従来から高速すぎて撮れない）。
  進捗ラベルの存在と遷移はコードと計測（フェーズ区間の実測）で確認済み。
  実機・書き出し版での見え方はオーナー確認待ち。
