# B-803 シェーダーの検査とフレーム時間の計測 — claude (2026-11-17)

- ブランチ: ai-native に直接反映（Q10 の承認による）。
- BACKLOG B-803: シェーダーのコンパイルエラーを行つきの JSON で返す。実行中のフレーム時間を測る。

## 内容

### シェーダーの検査（エンジン本体の変更）

- `servers/rendering/shader_check_json.{h,cpp}`（新規、エディター版だけ）:
  - エディタのシェーダー編集画面と同じ順で検査する: 前処理（ShaderPreprocessor）→ shader_type に合った関数・モードでのコンパイル（ShaderLanguage）→ 警告。
  - 描画（レンダラー）は要らない。ヘッドレスで動く。
  - 出力: `{"ok", "file", "shader_type", "errors", "warnings"}`。各項目は file・line・column（コンパイラは行しか出さないので -1）・code・message。
  - エラーの code: `SH`＋8桁。GDScript（B-202）と同じく、名前と数字を除いた文の形から作る。警告の code は警告の名前（UNUSED_UNIFORM など）。
  - include ファイル（.gdshaderinc）は include として検査し、「使っていない」系の警告は出さない。
- `main/main.cpp`: `--check-only --script <file.gdshader | .gdshaderinc>` で、この検査をして JSON を出す。終了コードは 0（ok）／1（エラーあり）。スクリプトの検査は変わらない。
- `servers/rendering/SCsub`: 新しいファイルを足した（このフォルダーはファイルを個別に書き並べる方式）。

### ツール

- `uzu.py engine check --path res://x.gdshader`: 上の JSON を返す。
- `uzu.py engine validate`: プロジェクト内のシェーダーも全部検査する。壊れたものは `shader_error`（行つきの errors 付き）として出す。
- フレーム時間: `ai_loop/selfplay/frametime.gd`（新規。bench.py が、プロジェクトのコピーに autoload として入れる）。
  - **work**: フレームの物理・処理の始まりから、最後に動くノードの _process までの時間。
    - ヘッドレスでは、各フレームの残りを待ち時間で埋めて、約 6.9 ms にそろえる。そのため、実時間ではゲームの重さが分からない。こちらで測る。
    - エンジンの Performance の値は1秒に1回しか更新されないので、フレームごとの値には使えない。
  - **wall**: フレーム間の実時間。描画あり（`--render`）のときだけ使う。
- `ai_loop/bench.py`:
  - 計測項目に `[Frame] work average／p95／worst`（描画ありなら `[Frame] wall ...` も）を足した。
  - フレームの項目は、揺れの下限を別に持つ（`--min-frame-ms`、既定 1 ms）。
  - `--render` で描画ありでも測れる。
  - 計測の前に、結果を捨てる1回を走らせる。作ったばかりのコピーでは、キャッシュ（.godot）を作る分だけ最初の1回が遅いため。
  - 終了処理（`[Shutdown] ...`）は、既定で合否の判定から外し、`ignored` として出すだけにした。`--include-shutdown` で判定に戻せる。
    - 理由: 終了処理の時間は、ゲームの中身と関係なく、約 20 ms と約 90 ms の2つのどちらかに揺れる。何もない素のプロジェクトでは 21〜25 ms で安定していたので、エンジンの終了待ちの揺れと判断した。
    - 実際、変更なしの比較が4回に1回 fail した。

## 確認

- 単体テスト: `tests/servers/rendering/test_shader_check_json.cpp`（新規、3件）
  - 正しいシェーダーは ok で、種類と UNUSED_UNIFORM の警告（2行目）が返る。
  - 未定義の名前は4行目のエラーになり、名前が違っても同じ code になる。
  - 別の種類の組み込み変数（canvas_item で ALBEDO）はエラーになる。
  - 前処理のエラーは行つきで返る。include は ok で、警告が出ない。
- 全テスト: **1484件中 1484 pass**（3件増えた）。ビルドの警告: なし。clang-format: pass。
- 手で試した: エラーのあるシェーダーは行5・code `SHB8EAEB75`・「Unknown identifier in expression: 'foo'.」が返り、終了コード 1。include を使うシェーダーと include ファイル単体は ok。
- `bench.py --self-test`（5回続けて ok）:
  - 毎フレーム 5 ms の処理を足すと `[Frame] work average` が悪化として出る。
  - 変更なしは pass する。
  - 終了処理の揺れは ignored に入り、`ignore=()` にすれば判定される。
- `uzu.py selftest all`（2回続けて ok）: engine に、シェーダーの検査（正しい／壊れた）と validate での検出を足した。

## 途中の失敗

- 最初は実時間でフレーム時間を測った。どのフレームも 6.9 ms になり、重くしても検出できなかった（ヘッドレスの待ち時間のため）。
- 次に Performance の値を使ったら 0 だった（1秒に1回しか更新されないため）。
- 自前で、フレームの始まりから最後の _process までを測る方式にした。

## 見つけた上流の不具合（申し送り）

- `--import` が、まれに終了時に異常終了する（SIGABRT、「Parameter "singleton" is null」at EditorNode::is_cmdline_mode）。
  - 原因の見当: 取り込みの後、エディタ本体が消えてから、遅れて実行されたファイル監視の更新（EditorFileSystem::_process_update_pending）がエディタ本体を参照している。上流の終了時の競合。
  - 起きる頻度: self-test 中に1回出た。同じ状態で12回繰り返しても再現しなかった。
  - 取り込み自体はその時点で終わっているので、`uzu.py engine import` では、エラーの記録なしに異常終了したら1回だけやり直す。結果に `retried` を出す。
  - エンジン側の修正（終了時にエディタ本体の有無を確かめる）は、再現をテストで固定する方法が決まってから、別の課題にする。
