# B-309 セーブステート（スナップショット／リストア） — claude (2026-11-18)

- ブランチ: ai-native に直接反映（リードの着手順。Wave 3 の推し3。判定に B-307 を使うので B-307 の後）。
- BACKLOG B-309: プレイ途中の状態を保存し、そこから分岐して再開できる仕組み（B-306 の制御の口から使う）。判定: サンプルゲームで中間の状態を保存 → 復元し、復元後の進行が B-307 のハッシュで一致すること。

## 内容（エンジン本体の変更なし）

- `state_hash.gd`（B-307）に `snapshot()` と `restore(snapshot)` を足した。
  - 対象: B-307 で宣言した状態と同じ。transform、メタデータ `uzu_state` のプロパティ、`uzu_state()` を持つノードはその戻り値。
  - 値はそのまま（Variant）で持ち、配列と辞書は深くコピーする（保存の後にゲームが中身を変えても影響しない）。
  - 復元では、transform とプロパティを戻す。`uzu_state()` を持つノードには `uzu_restore(Dictionary)` を呼ぶ（ゲーム独自の状態の戻し方）。
  - 乱数: 保存のときも復元のときも、スナップショットのフレームから決めた種で、グローバルの乱数をそろえ直す。「保存したまま進む」と「復元してから進む」が同じ乱数になる。
- 制御の口（`control.gd`、B-306）に命令を足した:
  - `save: 名前`: 状態と、そのとき押しているアクションをスロットに保存する。
  - `restore: 名前`: 状態とアクションを戻す。ないスロットは error を返す。
  - `hash: true`: 次の観測に `state_hash` を付ける。
  - 観測には saved／restored／restored_nodes が付く。
- `aiplayer.py`: 状態記録用の autoload も入れるようにした。`Game.save(name)`、`Game.restore(name)`、`Game.state_hash()` を足した。

## 確認

- `aiplayer.py --self-test`（判定の検査）: ok。
  - サンプルゲームで 100 フレーム右へ進み、最初の穴の手前で保存した。
  - 保存のまま、決めた入力（60 フレーム走る → ジャンプ → 90 フレーム走る）で進めたハッシュと、復元してから同じ入力で進めたハッシュが一致した。
  - 復元の直後の位置は、保存した位置から1フレーム分（4 px）だけ進んだ所（保存と復元の命令がそれぞれ1フレーム進むため。どちらも同じ）。
  - 同じ保存から別の入力（ジャンプなし）で進めると、ハッシュが変わる（ハッシュが意味を持っていることの確認）。
  - ないスロットの復元は error になる。
- `uzu.py selftest all`: ok（engine／selfplay／tools）。
- 全テスト: C++ の変更はないので、B-723／B-724 と同じバイナリで 1496/1496 pass。

## 限界

- 戻せるのは、ゲームが宣言した状態だけ。宣言していないもの（物理エンジンの内部の速度、アニメーションの再生位置、宣言していないノードの変数など）は戻らない。宣言を足すか、`uzu_state()`／`uzu_restore()` で自分で扱う。
- 保存はメモリーの中だけ（そのプレイの間）。ファイルへの保存はまだない（必要になったら足す）。
