# B-111 検証高速化（ccache＋テスト選択の常用）— Muse (lead branch)

ブランチ: agent/b-111-lead（worktree: ~/workspace/godot-speed、起点 fork/ai-native b09ea93d523）

## 仕事1: ccache 導入検証

- ccache 4.14.3（公式リリースの Linux x86_64 glibc バイナリ）を
  `~/workspace/tools/ccache/` へ導入。取得は GitHub Releases から成功したため
  sccache への代替は不要だった。
- キャッシュ置き場: `~/workspace/.ccache`（worktree をまたいで共有、上限 10GB）。
  設定（ccache.conf）: `max_size=10G`、`base_dir=~/workspace`、
  `hash_dir=false`（worktree ごとに異なる cwd をハッシュに含めない）。
- SCons への噛ませ方: PATH 前置のシンボリックリンク方式に確定。
  `~/workspace/tools/ccache/bin/{gcc,g++,cc,c++}` → `../ccache`。
  理由: SCons のビルド署名（コマンド文字列）を変えないので、既存の
  .sconsign や SCons キャッシュと競合せず、ccache の統計で効果を直接
  裏付けられる。CC/CXX 環境変数方式は Godot の SConstruct が環境変数を
  取り込む保証がなく、署名も変わるため採らない。
- 事前スモーク: 素の C ファイルで miss→hit を確認（統計 1 miss / 1 hit）。

### 計測方法

フルビルド同士の比較は、この VM（実効1.5コア）では1回数時間級で、
並行する B-1108 のビルドロック待ちも含め現実的でないため、代表サブセットで
厳密に A/B した。対象は scene/3d・scene/gui・scene/resources 直下の
editor オブジェクト 188 個（UZU 系: uzu_juice / uzu_look / uzu_ui /
uzu_ui_juice / uzu_sfx / uzu_post_effect 等を含む）。全 run とも
`platform=linuxbsd target=editor tests=yes accesskit=no arch=x86_64 -j3`、
同一対象リスト、ビルドロック（flock /tmp/uzu-build.lock）内で直列実行。

| run | 条件 | 実測（scons 内訳） | ccache 統計 |
|---|---|---|---|
| A | ベースライン（ccache なし、godot-speed） | 997s（16:29） | — |
| B | ccache 冷（godot-speed2、初回） | 1040s（17:09） | 189 misses |
| C | ccache 温・同一 worktree で対象オブジェクトを削除して再ビルド | 9s（4.03s） | 188 hits |
| D | ccache 温・**新規 worktree**（godot-speed3） | 17s（9.81s） | 189 hits |
| E | 増分: 1ファイル変更＋ccache（godot-speed3） | 7s（1.95s） | 1 preprocessed hit |
| F | 増分: 1ファイル変更・ccache なし（godot-speed） | 23s（13.03s） | — |

- 統計の総計（パイプライン実行分）: cacheable 567 件、hits 378 件
  （direct 377＋preprocessed 1）、misses 189 件。数え方は
  B=189 miss、C=188 hit、D=189 hit、E=1 hit で一致する。
- **新規 worktree の再ビルドは 997s → 17s（約 −98%）**。これが B-111 の
  判定の主結果。フルビルド全体（editor 対象は約3199オブジェクト）での
  実測はしていない。サブセットは全体の約6%で、リンクや生成工程は
  キャッシュ対象外のため、フルビルドの短縮率はこれより小さいはず。
  参考: 同時間帯の B-1108 のフルビルド（-j2）は約2時間20分だった。
- 冷えた状態の ccache はベースライン比 +4.3%（1040s vs 997s）。
  初回だけの小さなコストで、2回目以降の worktree から回収できる。
- 増分の E はコメントのみの変更で、前処理後の内容が同一のため
  preprocessed hit になった。実コード変更では miss になり実コンパイルが
  走る（F 相当）。つまり ccache は「新規 worktree／クリーン再ビルド」を
  速くするもので、1ファイル増分そのものは速くならない。想定どおり。
- ハマりどころ（重要）: 当初、統計が 0 件で「shim が効いていない」ように
  見えた。原因は、SCons がコンパイラ子プロセスへ渡す環境が PATH 等に
  限られ CCACHE_DIR と HOME が渡らないこと。ccache は getpwuid の
  フォールバックで /root/.cache/ccache（デフォルト、5GB 上限）を使って
  おり、workspace 側の統計読みが空振りしていた。実コンパイルは最初から
  shim 経由で動いていた（/root 側の統計 567 件が証拠）。
- 本番構成の確定: キャッシュ置き場を永続場所へ固定するため、
  /root/.config/ccache/ccache.conf に cache_dir=~/workspace/.ccache 等を
  置いた（HOME の無い子プロセスでも getpwuid 経由でこの設定ファイルに
  辿り着く）。温まったキャッシュ（189 件、22MB）も workspace 側へ移した。
  検証: 実ビルドと同一のコンパイルコマンドを env -i（PATH のみ）で実行し、
  250ms でオブジェクトが生成され、workspace 側キャッシュに direct hit が
  1 件記録されることを確認した。

### 判断

- ccache は「効く」。AGENTS.md のビルド節を ccache 前提（PATH 前置＋
  設定ファイルの所在）に更新した。手順はこの VM 向け。VM が差し替わった
  場合は、バイナリ導入と /root/.config/ccache/ccache.conf の再配置が要る
  （AGENTS.md の記述から再現可能）。
- SCons 側の SConstruct にもある c_compiler_launcher／cpp_compiler_launcher
  は使わなかった。PATH 前置で十分に効き、ビルド署名を変えない分、
  既存の .sconsign や SCons キャッシュと競合しないため。

## 仕事2: テスト選択の常用ラッパー ai_loop/verify_changed.py

- 基準（既定 fork/ai-native）との git diff（コミット済み＋作業ツリー＋
  未追跡）で変更ファイルを得て、B-105 の tests/select_tests.py の
  select／run_selection をそのまま再利用する薄いラッパー。
- 引数は --base / --binary / --catalog / --root / --run に絞った。
  カタログ（全件実行の B-101 JSON）が無い場合はバイナリで全件を1回回して
  生成する（選択の正しさはカタログの鮮度に依存するため、保存済みカタログの
  再利用を推奨し、その旨を docstring と AGENTS.md に明記）。
- 安全側のフォールバック: impact_map で解決できない変更（core/ の大半、
  ai_loop、文書など）は select_tests 側の設計どおり全件実行になり、
  理由（fallback_reasons）を標準エラーと JSON の両方に必ず表示する。
  さらに SConstruct / SCsub / methods.py の変更は「wide-impact」として
  選択結果があっても全件へ強制フォールバックする。
