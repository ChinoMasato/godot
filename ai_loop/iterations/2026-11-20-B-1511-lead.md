# B-1511 保存物の再読監査（lead branch）

生成・構築したシーンを、生成側の自己申告ではなく保存済みの .tscn を
再オープンして数え直し、B-1509 の spec set（asset_registry／scene_spec）と
突合する道具。B-1204 リッチ度レポート（描画の実測）とは別系統で、
こちらは保存物の忠実度を見る。C++ 変更なし（GDScript＋Python のみ）。
エンジン全テストは CI 担保。

## 数え直しの方式

- エンジン側 `ai_loop/audit_tool.gd`（extends SceneTree）が保存シーンを
  load → instantiate する。ツリーには入れない（副作用なしで数えるため）。
  ルートの直接の子を part とし、part ごと＋全体で集計して
  `AUDIT_RESULT {json}` を1行出す。`uzu.py` の gd_tool 経由で呼ぶ。
- 数えるもの: ノード数、メッシュの三角形数、テクスチャ（BaseMaterial3D の
  `*_texture` プロパティを走査し resource_path、無ければ instance id で
  dedupe、寸法つき）、MultiMesh の配置数、CollisionShape3D 数（disabled
  別集計）と PhysicsBody 数、Light3D 数、NavigationMesh のポリゴン／頂点数、
  シーンインスタンス数（path が "." でないもの）。ノード別明細
  （mesh_nodes／multimesh_nodes／collision_shape_names）も残し、突合側の
  規約が変わっても再計算できるようにした。
- 三角形数は2経路: ArrayMesh は `surface_get_array_index_len`／
  `surface_get_array_len`（圧縮フォーマットでも取れる）、それ以外は
  `surface_get_arrays`。基底 Mesh に長さ API は無いので PrimitiveMesh に
  誤って呼ぶと黙って 0 を返す事故になる——経路分離は必須。
- 入れ子の PackedScene（外部シーンのインスタンス）は instantiate で
  展開されるため、中身は内包する part の一部として数える。
  scene_instances は「何個の外部シーンが埋め込まれているか」の参考値。
- MultiMesh の配置数は二層で数える:
  - **保存数（正）**: テキスト .tscn を Python 側でパース
    （`audit_scene.parse_tscn_multimeshes`）。instance_count プロパティが
    あればそれ、無ければ buffer の float 数 ÷ stride（transform_format
    0→8／1→12、use_colors・use_custom_data で各 +4）。
  - **ロード数**: エンジンが実際に読み込んだ get_instance_count。
    保存数 ≠ ロード数は load_fidelity チェックとして別枠で差分に出す。
- バイナリ .scn はテキストパース不可（None を返し、保存数はロード数に
  フォールバック、load_fidelity は出さない）。対照確認: map_tool が
  外部 .res（バイナリ）で保存した自然マップは instance_count ごと
  正しく読める（nature の見本で generator counts と一致）。

## 突合のスキーマ（uzu-scene-audit/1）

`ai_loop/audit_scene.py` が recount＋保存数＋spec set からレポートを作る。
check は {id, kind: registry|observed|load_fidelity, status:
match|difference|not_countable, expected, actual, note}。ok は
difference が 0 件のとき。主な対応規則（docstring にも明記）:

- measure="triangles": `terrain_mesh` は part 内の "Terrain" という名前の
  メッシュノード。`meshes`（街）は part の全メッシュノード三角形＋
  MultiMesh 三角形（保存数ベース）から、インスタンスとして数える散布
  family（街路樹・木・岩・草）の MultiMesh 三角形を差し引いたもの。
  ただし windows family が消費する WindowFrames MultiMesh は差し引かない
  （生成器の合計定義にフレームが含まれるため——生成器固有の知識として
  ここに明記する）。
- インスタンス系: MultiMesh は正規化名（小文字英数字のみ）の完全一致、
  無ければ stem（末尾 s を落とす）前方一致グループ（trees →
  TreesBroadleaf＋TreesConifer、windows → WindowFrames_*）。保存数を正とする。
- 当たり系: CollisionShape3D 名から末尾の [0-9_]+ を落としたキーと
  family の単数形キーの一致（buildings→building、benches→bench 等）。
- "lights" は Light3D ノード数。
- 構造が無い family は actual=0 として差分に出す（消えた部品が
  not_countable に化けて見逃されるのを防ぐ）。ただし数えられないことが
  構造的に決まっているものは明示リストで not_countable にする:
  lamps（柱は1メッシュに融合）、windows_lit（融合メッシュ）、
  empty_lots（不在そのもの）、buildings_detail（detail 辞書のキー数）、
  parts（dict 型 count）。count_basis が observed でない family も
  not_countable。
- observed の突合は navigation.polygons／vertices のみ（places と counts は
  registry と重複するため再チェックしない）。
- レポートの measured.collision（shapes／bodies／part 別内訳／
  parts_with_collision）が、B-1509 で Unverified のまま残った
  collision_coverage の証拠になる形にした。spec_set.py 本体は変更しない
  （B-1510 の流儀どおり、証拠レポートを spec_set/ に並べる）。

口: CLI `uzu.py audit-scene <project> --scene res://x.tscn [--spec-set DIR]
[--out report.json]`（spec-set 省略時はシーン隣の spec_set/ か
<scene>_spec_set/ を自動探索）、MCP `scene_audit`。カタログ再生成済み
（total 217）。

## 見本の結果（hikari の生成済み村、audit_check.py で再生成可能）

spec_set/scene_audit_report.json: **match 23 / difference 6 / not_countable 5**。

一致した主なもの: 建物 6・ベンチ 4・ブロック 9・街路樹 26・窓枠 37・
ライト 2、Land 地形 8192 三角形、Land 散布の保存数（広葉樹 537／針葉樹
433／岩 78／草 3273）、Village の Navigation 652 ポリゴン／603 頂点、
当たり判定 22 形状／4 ボディ、テクスチャ 12 枚（240×240 が 9 枚、
256×256 が 3 枚。registry にテクスチャの期待値が無いため実測の提示のみ）。

### 既知の差分（3種、いずれも監査が見つけた実物側の事実）

1. **Village/meshes: 申告 6746 に対し実物 12272（生成器の自己申告バグ）**。
   合体メッシュ 3984＋窓枠 37×224＝8288 が実物。申告値は
   3984＋2762＝6746 で、2762 は 37×224/3 の切り捨て。
   原因は modules/uzu_worldgen/uzu_world_gen.cpp:2832 の式
   `frames_total * frame_mesh->get_faces().size() / 3`:
   C++ の `Mesh::get_faces()` は Face3（三角形そのもの）の配列を返すので
   `.size()` は既に三角形数 224 で、さらに /3 する二重割り算になっている
   （GDScript バインディングの get_faces が頂点配列を返すのとの混同と
   見られる）。**生成器本体の修正は本項目の範囲外。リードへの申し送り**:
   2832 行の /3 を外すのが修正箇所で、修正後は registry の meshes が
   実物と一致するはず。
2. **Pond/terrain_mesh: 申告 2048 に対し実物 1024**。main.gd の
   _trim_terrain が市の境界で池地形を切断したため。spec record の
   context 自体が「ゲーム側の生成後調整は記録の対象外」と宣言している
   調整であり、生成器の申告ミスではない。
3. **load_fidelity ×4（Land の MultiMesh）**。合成した village.tscn では
   Land の4つの MultiMesh（TreesBroadleaf／TreesConifer／Rocks／Grass）に
   buffer は保存されているが **instance_count プロパティが書かれて
   いない**。ロード時はプロパティ順に transform_format → mesh → buffer と
   適用され、buffer 設定時点で count が 0 のため
   `MultiMesh::set_buffer` が早期 return して buffer が捨てられる
   （scene/resources/multimesh.cpp で確認）。結果、エンジン再読では
   Land 散布が 0 になる。対照データ: 街の MultiMesh（WindowFrames／
   StreetTrees）は instance_count が書かれており正常に読める。map_tool の
   保存は inline でも instance_count が書かれる。外部 .res 保存も正常。
   つまりこの欠落は compose_village 経路（PackedScene.pack＋
   ResourceSaver.save でインライン化）特有。なぜ saver が Land 分だけ
   instance_count を省いたかの機構は未解明（_trim_scatter の関与が候補
   だが、保存された buffer はトリム前の全数だったため断定しない）。
   現象と対照データのみ記録する。監査は保存数を正として突合するので、
   registry との照合自体は正しく行える。

## 反証（部品を1つ消す）

`ai_loop/samples/hikari/audit_check.py`: 一時コピーで村を合成 → 監査 →
コピーの village.tscn から WindowFrames_0_1 ノードブロック（窓枠12個）を
削除 → 再監査。結果（spec_set/scene_audit_report_removed.json）:
ベースラインの差分集合に **windows 37→25 と Village/meshes −2688
（12枠×224三角形）だけ** がちょうど加わり、他の check の status は
一切変わらない。audit_check.py はベースライン差分の期待集合と合わせて
機械 assert し、ok: true で終了した。

## できなかったこと・限界

- ShaderMaterial のシェーダーパラメータ経由のテクスチャは数えていない
  （BaseMaterial3D のみ）。見本の村は全て BaseMaterial3D なので実測に
  影響なし。
- バイナリ .scn の保存数パースは不可（ロード数にフォールバック）。
- instance_count 欠落の機構は未解明（上記3参照）。compose 経路の保存は
  監査で検出できるが、直すなら compose_village／saver 側の別項目。
- 生成器の三角形二重割り算（差分1）は申し送りのみ。本項目では直さない。
