# B-1223 仕様差分検証（2026-11-20、Muse / lead branch）

仕様イラストと、基準カメラで撮ったシーンのスクリーンショットを機械的に比較し、「どこがどれだけ違うか」を要素単位の合否 JSON で返す道具を実装した。B-1221 が「画像→雛形」の生成側、本項目が「画像 vs 実物」の検証側で、イメージ先行フローのループが閉じる。

## 実装

- **`ai_loop/spec_diff.py`（新規、標準ライブラリのみ）**: 比較の中核。純関数 `compare(spec_path, shot_path, elements, thresholds) -> verdict`（形式 `uzu-spec-diff/1`）。PNG 読みと縮小は image_scene（image_diff）を再利用。比較は B-1221 レポートの作業解像度（上限 768 幅）で行う。
  - **構図**: 輝度の勾配エッジ同士の一致度。相手側エッジをぼかして（3×3 box blur 2回）から照合する対称スコアで、±2px 程度の位置ずれは吸収する。
  - **色調**: 4×4×4 RGB ヒストグラムの距離（1 − 交点）。
  - **要素の有無**: 要素ごとに3つの信号を測り、全数値を返す。(a) ゲイン補正つき画素一致率——トーンマッピングで明部が暗くなるため、領域の平均色に合わせてショット側を再露出してから画素を比べる。ただし平均色距離が上限（0.45）を超える場合は一致率を無効にする（露出補正はトーンマッピングの模型であって、別の色への塗り替えまで吸収させない。単体テストで「扉を壁色に塗り替えると一致率 1.0 になる」失敗を実際に踏んで入れた歯止め）。(b) 領域の平均色距離。(c) 周囲（リング）に対する際立ちの比（ショット／仕様）。判定規則は種別で変える: カードは (a) 一致率 ≥0.5、または (b)(c)＋内部エッジ密度の複合。候補（glow／door）は (a)、(b)(c)、または「際立ちの比 ≥0.25 かつ明暗の向きが一致」でも pass——ランプは実物では光源であって描かれた光の塊ではないので、画素一致が低くて当然の要素があるため。
  - **要素の出所**: `elements_from_report()` が B-1221 レポート（layers.cards＋candidates.interact）から {id, kind, bbox, basis} を作る唯一の場所。B-1222 のレジストリができたら同じ形を差し込める。
  - **閾値**: 全部データ（DEFAULT_THRESHOLDS）。`--thresholds` の JSON と個別フラグでプロジェクト側から上書きでき、未知キーはエラーにする。既定値は見本の実測で決めた（下記）。
- **`uzu.py spec-diff <project> --spec-image ... [--report ...] [--scene ...] [--shot-png ...] [--thresholds ...] [--out ...]`**: 基準カメラのシーンを撮影（既存 screenshot の Movie Maker 経路）して比較する。`--shot-png` で既存スクリーンショットの再利用も可。spec_diff.py 単体でも（エンジンなしで）実行できる。
- テスト: `ai_loop/tests/test_spec_diff.py`（6件、selftest tools に登録）。`ai_loop/spec_diff_check.py` が実エンジンでの反証を通しで確認する。カタログ再生成 230件（cli spec-diff、script spec_diff／spec_diff_check を登録）。

## 見本の実測（ai_loop/samples/image_scene、基準ショットは B-1221 の reference.png と新規撮影の両方）

- 仕様どおりの画面: 構図 0.416（新規撮影 0.419）／色調距離 0.200（新規撮影 0.313）／要素 14件全 pass → 総合 pass。閾値の既定は構図 ≥0.30、色調 ≤0.32。
- 要素の内訳: カード6件と glow_0〜2、door 2件は画素一致（0.68〜1.0）で pass。遠景の小窓 glow_3〜5（10×13px）は画素一致 0.05〜0.07 しかない（霧とトーンマッピングで描かれた明るさが残らない）が、際立ちの比 0.41／0.35／0.30 で pass した。候補の閾値 0.25 に対する余裕は薄い。
- 反証1（要素消去）: Card_Midground_3（街灯の柱）を spec から外し、背景画の同領域を行方向の背景延長で塗り替えて再構築 → 総合 fail、fail した bbox は消した要素のものだけ（door_0 は同じ bbox の別解釈で同一視）、他のカードは全 pass、全体指標（構図・色調）は pass のまま。狙いどおり「その要素だけ fail」。
- 反証2（色調変更）: シーンのテクスチャ全ての R/B を入れ替え → 色調距離 0.601 で色調指標だけ fail（構図は 0.399 で pass のまま）。

## 限界・できなかったこと

- 大きく平坦で低コントラストな要素（見本の家のシルエット等）は、消去の検出が本質的に弱い。仕様画像の中でも周囲との際立ちが 0.03 程度しかなく、背景延長で塗ると平均色も画素一致も大きくは動かない。今回は街灯の柱で反証を示した。家の欠落は要素単位ではなく全体の構図スコアの低下として現れる側。
- 色調距離は撮影ごとのばらつきがある（同じシーンで 0.200 と 0.313）。閾値 0.32 は見本では pass だが余裕は薄く、プロジェクトごとに `--thresholds` で調整する前提。ばらつきの主因（フレーム位置、バイナリ差）の切り分けはしていない。
- 画素一致は ±3px の位置ずれまでしか追わない。カメラや配置が大きくずれると要素は「無い」側に倒れる（構図スコアも下がるので、ずれ自体は検出できる）。
- 入力は PNG のみ（image_diff と同じ制約）。ショットのアスペクトが仕様と 3% 以上違う場合は引き伸ばして比べ、注記を返す。
- MCP への露出はしていない（B-1221 と同じく CLI が入口。必要なら後続で）。
