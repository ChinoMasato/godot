## 内容

- **エンジン**（`core/error/error_log_json.cpp`）: B-201 の JSON ログの各行に `frame`（エラーが起きた処理フレーム）を足した。項目の追加だけなので、既存の読み手は変わらない。
- `uzu.py selfplay ... --packet フォルダ [--expect-clear]`:
  - 失敗の判定: エラー（error／script_error）がある、終了コードが 0 でない、または `--expect-clear` を付けたのにクリアしない。失敗なら ok: false。
    - スクリプトのエラーはそのフレームの処理を止めるだけで、ゲームは続く。そのため、`--packet` を付けたときはエラーを失敗として扱う。
  - 失敗したときだけ、フォルダに次のものを書く:
    - `packet.json`: 理由、原因の場所 `where`（file・line・function。スクリプトのエラーならその位置、エンジン側のエラーなら B-103 のスクリプトの位置）、最初のエラー、失敗のフレーム、その時点の状態、チェックポイント・死亡・クリア、レポート、種、再実行のコマンド、ファイルの一覧。
    - `errors.jsonl`（全エラー）、`events.jsonl`（テレメトリ）、`replay.json`（入力）、`state.json`（失敗時点の状態。B-307 の宣言）、`failure.png`（失敗時点の画面）。
  - 画面と状態の取り方: 同じ入力・同じ種・固定 FPS で、失敗のフレームの次まで描画ありで再生する。再生は決定的なので同じ所で止まる。描画できない環境では、状態だけを取る。

## 途中の失敗

- 自分の検査が、エラーがあれば ok が false になる前提だった。実際はゲームが続くので、終了コード 0 で ok のままだった。`--packet` のときは失敗を ok: false にした。
- 失敗の時点の状態が、1フレーム手前（位置 496）になった。エラーが起きたフレームの処理まで含めるため、再生を「そのフレーム＋1」までにした。
- チェックポイントの一覧を「cp1・cp2 だけ」と検査していたが、ゲームは続いて cp3 まで進む。「cp2 を含む」に直した。
