# B-806 `--import` の終了時の異常終了（上流の競合） — claude (2026-11-18)

- ブランチ: ai-native に直接反映（Q10 の承認の続き。B-803 で見つけた上流の不具合）。
- BACKLOG B-806: 取り込みの後、エディタ本体が消えてから遅れて動く処理が、エディタ本体を参照して落ちる。判定: 再現をテストで固定し、そのテストが pass すること＋全テスト pass。

## 原因

- `EditorNode::is_cmdline_mode()` は、エディタ本体（EditorNode）がないとき、「Parameter "singleton" is null」というエラーを出して **false**（コマンドラインではない）を返す。
- 終了の途中（エディタ本体の解放の後）に遅れて動く処理が、この false を見て「エディタ向けの処理」を続け、解放済みの部分に触れて SIGABRT で落ちていた。
- 呼び出し元は2か所あった:
  1. `EditorFileSystem::_process_update_pending`: スクリプトのドキュメントとシーンのグループの更新。
  2. `EditorHelp::load_script_doc_cache`: スクリプトのドキュメントのキャッシュ。初めての取り込みではキャッシュがないので、別スレッドで作り直しに進む。
- 最初は 1 だけを直した。実際に繰り返し試すと、まだ 20 回中 1 回（作ったばかりのプロジェクトでの最初の取り込み）落ちた。ログから 2 の呼び出し元を見つけて、そこも直した。

## 内容（エンジン本体の変更。上流のエディタのコード）

- `EditorFileSystem::can_update_editor_data()`（新規、static）: エディタ本体があり、かつコマンドラインでないときだけ true。本体の有無を先に確かめるので、エラーを出さない。
- 上の2か所（`_process_update_pending` と `EditorHelp::load_script_doc_cache`）を、この関数で判定するようにした。スクリプトのクラスの更新（`_update_script_classes`）は今までどおり行う。
- `ai_loop/uzu.py` の取り込みの「異常終了なら1回やり直す」は、害がないので保険として残し、注記を直した。

## 確認

- 単体テスト: `tests/editor/test_editor_file_system_exit.cpp`（新規）。終了時と同じ「エディタ本体がない」状態で、次を固定した。
  - `can_update_editor_data()` が false になり、エラーを出さない。
  - 対照: 以前の判定（`is_cmdline_mode()` だけ）では、エラーを出して false（＝エディタ向けの処理を続ける側）を返す。これが不具合の入口だった。
- 実際の `--import`（ツールのやり直しを通さず、直接呼ぶ）:
  - 修正前: スクリプトとシーンのあるプロジェクトで、作ったばかりの状態からの取り込みで落ちた（B-803 の self-test で1回。今回の 20 回の試しでも1回）。
  - 修正後:
    - 同じプロジェクトで 20 回続けて取り込み、異常終了 0 回。
    - 毎回キャッシュ（`.godot`）を消して「最初の取り込み」にした 15 回でも、異常終了 0 回。
- 全テスト: **1497件中 1497 pass**（1件増えた）。ビルドの警告: なし。clang-format: pass。
- `uzu.py selftest all`: ok。
