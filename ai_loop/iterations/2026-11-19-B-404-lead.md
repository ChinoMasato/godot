## 実装

### (1) 能力プロファイル — ai_loop/agent_caps.py（新規）
- 能力の語彙は KNOWN_CAPABILITIES = blender / browser / gpu / image_gen。未知の能力名は CapsError（検証エラー）で、黙って無視しない。
- 宣言は2経路＋引数、マージされる: 環境変数 `UZU_AGENT_CAPS`（カンマ区切り）、JSON プロファイルファイル（`UZU_AGENT_PROFILE` または `--profile`、`{"capabilities": [...]}` 形式／裸のリストも可）、コマンド引数 `--caps`。
- `uzu.py caps` で有効プロファイルと出所（sources）を構造化出力で確認できる。

### (2) カタログ連携 — make_catalog.py / catalog.py / mcp_server.py
- 宣言は定義の近傍に置き、生成器が拾う（二重管理なし）:
  - MCP: mcp_server.py の TOOLS 直後に `TOOL_CAPABILITIES`（現行の宣言は frame_benchmark → gpu、代替は「render なしのヘッドレス計測」）。
  - スクリプト: モジュール先頭の `CAPABILITIES` リテラル（blender_bridge.py → blender、代替は既製 GLB かエンジン内構築。texture_route.py → 能力不要＋適応の説明）。
  - CLI: uzu.py が委譲するモジュールの CAPABILITIES（CLI_MODULES 経由）。
  - command エントリへは、MCP ツールが一意に対応する場合だけ写す。
- 全エントリに `required_capabilities`（既定は空）と `fallback`（既定は null）が付く。生成器は能力名を agent_caps で検証する。カタログは 193 → 197 件（cli caps／texture-route、script agent_caps／texture_route が増えた）。
- `uzu.py catalog <単語> --caps a,b` / `--profile file`: プロファイルがある場合だけ、一致エントリを隠さず `missing_capabilities` を注釈し、結果に profile と profile_sources を含める。プロファイル源が無ければ B-403 の出力のまま（後方互換）。MCP の catalog_search にも caps／profile 引数を追加（mcp_server の self-test に確認を追加）。

### (3) 構造化フォールバックの実例 — ai_loop/texture_route.py（新規、`uzu.py texture-route`）
テクスチャ生成の経路を能力で振り分ける。どちらの結果にも route と reason（決め手の能力）が入る。
- image_gen あり → generated_image ルート（生成画像→UZUPBRFromImage、B-902 の `picture pbrmake`）。画像が無い場合は ok:false＋needs_input:"image"＋手続きルートへの fallback を返す（失敗で終わらせない）。画像が実在すれば next_steps を返す。
- image_gen なし → procedural_preset ルート（B-1209）。プリセット一覧は engine_tool.gd の PBR_PRESETS 定義から読む（brick／dirt／grass／plaster／stone／tile／wood）。--preset 指定で適用コマンド（`uzu.py look <project> pbr --assign ...`）まで返す。不明なプリセットは一覧つきエラー。
