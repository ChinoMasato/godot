# B-1109 VFX recipes — composite effects from declarative recipes (lead branch)

## What was built

`UZUVfx` (new class, `scene/3d/uzu_vfx.{h,cpp}`, doc page
`doc/classes/UZUVfx.xml`): a recipe (Dictionary / JSON) describes a composite
effect as a list of parts; one call fires the whole thing and returns the
normalized recipe plus what was actually fired.

Parts: `sparks` (CPUParticles3D burst, additive billboards), `smoke`
(rising soft-particle puffs), `debris` (tumbling box shards under gravity),
`ring` (expanding shockwave torus lying flat, fading out), `beam`
(origin→target cylinder, additive, fading), `light` (OmniLight3D flash that
decays linearly), plus delegation parts `shake` / `hitstop` / `kick`
(UZUJuice) and `sfx` (UZUSfx preset names). Parts carry `at`
(`origin`/`target`) and `delay` (seconds before the part starts).

API (all static, mirroring UZUJuice's shape):

- `validate_recipe(recipe)` → `{ok, name, parts, duration, warnings,
  errors}` — pure value function: fills every default, clamps out-of-range
  numbers (recorded in `warnings`), rejects unknown part types, unknown
  keys, wrong value types, bad colors and unknown sfx presets (`errors`).
  `duration` = max(delay + part span) + 0.25 s tail.
- `describe_recipe(name)` / `get_recipe_names()` — the built-ins, validated.
- `fire(parent, position, recipe, target)` / `fire_between(...)` /
  `fire_named(...)` / `fire_named_between(...)` — builds one effect root
  (Node3D) with a child node per part under the caller's parent, starts
  tracking, returns the validation result plus `fired` (the part types that
  produced nodes or side effects).
- `get_active_count()` / `get_active_effects()` — pure-value snapshot of
  live effects (name, age, duration, per-part type/started/done), the
  UZUJuice "state as values" pattern.
- `apply_effects(dt)` — advances ages: starts delayed parts, grows the
  ring, decays the light, frees finished effects. `UZUVfxRuntime` (a Node
  added to the tree root on first fire) calls it every frame with
  wall-clock delta, like UZUJuiceRuntime.
- `clear_effects()` — frees every live effect root.

Built-in recipes:

- `explosion` — debris (14) + sparks (42) + smoke (14, delay 0.08) + ring
  (r 2.2) + light (energy 4, range 6) + shake 0.55 + hitstop 0.05 +
  sfx `explosion`; duration 1.93 s.
- `laser` — beam (0.18 s) + sparks at target (18, cyan) + light at target
  (energy 3) + sfx `laser`; duration 0.68 s.

## Design decision: new class, not a UZUJuice extension

UZUJuice's parts act on *existing* nodes (a target's material, the camera)
or on global state (trauma, time effects). A recipe instead *creates* a set
of short-lived effect nodes and tracks them until they die — a composition
layer above the parts, with its own lifetime bookkeeping. This is the same
split UZUSfx already made (sound synthesis separated from UZUJuice), and it
keeps UZUJuice's API surface unchanged. Juice parts that need no target
(shake, hitstop, kick) and UZUSfx presets are reused by delegation.
`flash` and `squash` are deliberately **not** recipe parts: both need a
target node, which a position-fired recipe does not have (stated in the
class doc). A real destruction simulation is out of scope by spec; the
`debris` burst stands in for it.

## Safety points (from past incidents)

- No function-static Ref is kept: the smoke texture is generated per fire
  (static caches of Refs crashed at exit before).
- The `sfx` part is skipped (and reported in the result's `skipped` list)
  when AudioServer is unavailable, instead of touching UZUSfx's synthesis
  in an audio-less environment (the B-1106 SIGSEGV).
- Tests never memdelete nodes inside the tree; effect roots are freed via
  `clear_effects()` / natural expiry, test parents are plain memnew'd
  anchors outside the tree.

## Tool surface

- CLI (`engine_tool.gd`): `vfx` (`--name explosion` or `--recipe '<json>'`)
  prints the validated recipe; `vfx-recipes` lists the built-ins.
- MCP: `vfx_describe` (one recipe, by name or JSON) and `vfx_recipes`.
- Catalog regenerated: 211 entries (was 204), `catalog vfx` finds the two
  commands, the two MCP tools and the class.
- Sample `ai_loop/samples/vfx/`: ground, boxes, sun, sky and a camera;
  fires the built-in explosion and a laser-shaped recipe between two
  points. Firing is keyed to frame numbers because effect lifetimes are
  wall-clock (UZUJuice's rule) while a software-rendered capture frame can
  take ~1 s of wall time — in a running game, fire once when things
  happen. Screenshot verified: beam, expanded ring, sparks, debris and
  the light flash are all visible mid-flight.

## Not done / notes

- BACKLOG B-1109 is left open for the lead to close; CLAIMS updated.
- Effects age by wall-clock delta (same rule as UZUJuice), so
  `Engine.time_scale` slow motion does not slow VFX down; hitstop still
  reads as a freeze because particles are CPUParticles (engine-scaled).
  If a game wants slow-motion effects, that is a future option on the
  runtime, not a change to the value layer.
- No per-part easing curves or looping/ambient effects (auras, rain):
  recipes are one-shot composites by design.
