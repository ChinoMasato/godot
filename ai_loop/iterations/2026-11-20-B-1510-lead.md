# B-1510 地域グラフと経路の自動歩行検証（2026-11-20、Muse lead branch）

B-1509 の region_graph（uzu-region-graph/1）を入力に、全辺を双方向へ
AI プレイヤー相当の体で実歩行し、経路単位の合否 JSON を残す道具を作った。
B-1504 の静的連結チェックと B-1507 の NavigationMesh 判定（単体）を、
「実際に体が着いた」という証拠に格上げする位置づけ。実装は GDScript
（歩行体）と Python（CLI／検証）のみで、**C++ 変更なし**。

## 使い方

- CLI: `uzu.py map <project> walk-graph --graph region_graph.json
  [--scene res://x.tscn] [--seconds N] [--block-node <id>] [--out report.json]`
  （scene 省略時はグラフの `scene`、無ければプロジェクトのメインシーン）
- MCP: `map_walk_graph`（graph 必須、scene／seconds／block-node 任意）
- 前提条件: グラフが指すシーンに生成済みマップが実在すること（道具側で
  明示チェックし、無ければ生成・合成を促すエラー）。NavigationMesh の
  ベイクは非同期なので、歩行開始前にマップの初回イテレーションを待ち、
  各脚のテレポート後も着地（is_on_floor）を待ってから計時する

## 歩行方式（ai_loop/selfplay/graph_walk.gd）

B-1507 の walk.gd と同じ体（カプセル CharacterBody3D、速度 4 m/s、
段差 0.25 m、重力・衝突あり）を全辺×双方向に使う。脚ごとに開始点へ
テレポートし、次の4モードで目標へ進む。

- **nav**: メッシュ上にいるとき NavigationServer3D の経路を辿る。
  「メッシュ上にいる」は高さ込みで判定する（最近点が歩行者の足元より
  一段以上上にある場合は乗っていない。土台スラブ上面を見て乗っている
  と誤判定したのが初期版のバグで、下記 Land の件の原因だった）
- **direct**: メッシュ外（自然地形にはメッシュが無い）では目標へ直進
- **seek**: direct が塞がれたら最寄りのメッシュ点（歩行可能なネット
  ワーク）まで歩き、そこから経路に乗る。同じ seek 点の繰り返しは打ち切る
- **wall**: メッシュが真上にあるのに段差で乗れない場合（土台スラブの
  縁）は壁沿いに進み、毎フレーム試みる段差登りで外側の地形が高い所から
  乗る。詰まったら一度だけ反転、窪地なら入り直して反対方向から

詰まり判定は2系統: 目標距離が 0.5 m 以上縮まらない状態が 5 秒、または
実移動が無い状態が 3 秒で、上記のフォールバック連鎖（nav→direct→
seek→wall→fail）を一段進める。脚の上限時間は辺の長さから
（30 + 長さ×1.25 秒、45〜600 秒にクランプ。--seconds で上書き可）。

## 合否 JSON のスキーマ（format: uzu-walk-graph-report/1）

- トップ: `ok`（全辺 pass で真）、`scene`、`blocked_node`（封鎖指定時）、
  `nodes`／`edges`／`legs` の数、`edges_ok`／`edges_failed`、`results`
- 辺ごと: `{a, b, length, ok, legs[2]}`。ok は両脚到達のときに限る
- 脚ごと: `{from, to, reached, frames（物理フレーム）, seconds, walked_m,
  used_nav, seeks, walls, stuck_at（失敗時 [x,y,z]）, left_m, reason
  （stuck|timeout）, on_wall, on_floor, hits（衝突相手と法線）}`

## 見本の結果（hikari の生成済み村、ノード16・辺13・26脚）

再現手順は `ai_loop/samples/hikari/walk_graph_check.py`（一時コピーに
compose_village.gd で village.tscn を合成 → walk-graph を2回実行 →
レポートを spec_set/ へ保存し、反転が1辺だけかまで機械確認する）。
所要は全体で約30秒。結果は `spec_set/walk_graph_report.json`:

- **10/13 辺 pass**。全26脚に合否・フレーム数・秒数が出る
- fail 3辺はいずれも証拠つきの正直な fail:
  - `Village__spawn ↔ Village__tallest_roof` と `Village__gate_west ↔
    Village__tallest_roof`: 屋根の上は歩いては立てない（B-1509 の引き継ぎ
    通りの設計）。上り脚は建物の壁（CityBody）で停止、下り脚は屋根から
    落ちて到達する非対称もそのまま記録される
  - `Land__clearings_1 ↔ Land__spawn` の進入方向のみ fail: 市は高さ
    0.5 m の土台スラブ（B-1508 で main.gd が敷いた CityFoundation）の
    上にあり、段差 0.25 m の歩行者は外側の地形がスラブ上面近くまで
    上がる所でしか入れない。歩行者は周囲を 178 m 壁沿いに進んだ末、
    スラブ東面と池地形の急斜面に挟まれた窪地 (5.9, −0.8, −15.4)
    （衝突相手: CityFoundationBody と TerrainBody）で停止した。
    逆方向（市から出る）はスラブを落ちるだけなので pass。
    **所見: 生成した市への徒歩の進入は、土台スラブの縁が実質の堀に
    なっている。** ゲーム側はプレイヤーをプレイ領域にクランプするので
    実害はないが、Land の place を市の外の拠点として使う生成をするなら
    入口（スロープか段差の緩和）が要る

## 反証（通れない経路の仕込み）

`--block-node Village__gate_east` で、そのノードの中心を高さ 3 m の
壁4枚で囲ってから歩く（結果は `spec_set/walk_graph_report_blocked.json`）。
gate_east は葉ノード（接続辺は plaza との1辺だけ）:

- fail 辺はベースラインの3辺＋ `Village__gate_east ↔ Village__plaza`
  の**ちょうど1辺だけ増加**し、他の辺の合否は不変（walk_graph_check.py
  と Python テストの両方で機械確認）
- 囲まれた内側からの脚はフェンス際 (1.2, 0.0, −9.9)、外からの脚は
  (−0.0, 0.0, −11.7) で停止し、衝突相手は UZUBlockFence と記録される

## できなかったこと・残り

- Land__clearings_1 → Land__spawn を通すところまでは歩行者を賢く
  しきれなかった（上記所見の通り、世界の側の性質でもある）。
  壁沿いの方向選択に地形の高さの先読み（レイキャストで段差を測る）
  を足せば市の西側の高い所から入れる可能性はあるが、本項目の判定
  （全経路の合否＋反証）には不要と判断して打ち切った
- validation_report の walk_reachability（B-1509 で Unverified）は
  spec_set.py を変更しない範囲とし、置き換えではなく証拠レポートを
  同じ spec_set/ に並べる形にした。spec_set 側で歩行レポートを
  evidence として取り込むのは次の改善候補
- MCP の call_tool はタイムアウト 600 秒固定のため、大きなグラフでは
  CLI が正の経路（見本規模では問題なし）
